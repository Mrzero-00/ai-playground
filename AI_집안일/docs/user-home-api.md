# 사용자·집 API 기준

기준일: 2026-08-11

## 1. 결정

MVP의 데이터 원본은 Supabase PostgreSQL이다. 브라우저의 `localStorage`는 최초 표시와 일시적인 장애 대응을 위한 캐시로만 사용하며, 공동 집의 최종 상태를 결정하지 않는다.

클라이언트는 Supabase를 직접 호출하지 않는다. 앱인토스 익명 식별키 또는 서명 쿠키를 Vercel API가 검증하고, 서버 전용 Supabase Secret Key로 데이터에 접근한다. 이 경계를 유지하면 추후 별도 API 서버로 이전해도 화면의 계약을 유지할 수 있다.

```text
앱인토스/웹 → Vercel API → Supabase PostgreSQL
      캐시         인증·인가       원본·트랜잭션
```

기존 `GET/PUT /api/state`는 화면의 점진적 이전을 위해 임시 호환 API로 유지한다. 새 기능은 사용자·집 리소스 API와 동작(action) API에 추가하고, 모든 화면이 이전된 뒤 전체 스냅샷 쓰기를 제거한다.

## 2. 데이터 책임

| 영역 | 원본 데이터 | 계산 데이터 |
| --- | --- | --- |
| 사용자 | 표시명, 생성일, 상태, 개인 알림 설정, 현재 집 | 완료 수, 집안일 레벨, 성향, 분류별 완료 수 |
| 집 | 이름, 아이콘, 시간대, 집 프로필, 운영 상태 | 오늘 예정/완료 수, 최근 활동 시각 |
| 소속 | 사용자와 집의 관계, 역할, 참여 시각, 활동 상태 | 현재 집에서 가능한 권한 |
| 집안일 | 반복 규칙, 다음 예정일, 분류, 활성 상태, 선택 담당자 | 예정 건(occurrence) |
| 완료 이력 | 예정일, 실제 수행자, 수행 시각, 당시 제목·분류·담당자, 상태 | 리포트, 기여 현황, 사용자 성향 |

`집에 사는 인원 수(householdSize)`와 `앱에 참여한 구성원 수(activeMemberCount)`는 다른 값이다. 아이는 나이만 계속 덮어쓰지 않고, 후속 마이그레이션에서 기준일이 있는 항목으로 확장한다. 반려동물은 종류 목록과 마릿수를 따로 받지 않고 `{ type, count }` 배열로 정규화하는 것을 목표로 한다.

## 3. 사용자 프로필 규칙

- 레벨과 성향은 중복 저장하지 않고 서버가 완료 이력에서 계산한다.
- 완료 당시의 `categorySnapshot`을 사용하므로 집안일을 삭제하거나 분류를 바꿔도 과거 성향이 변하지 않는다.
- 취소된 완료는 계산에서 제외한다.
- 기본 레벨 공식은 완료 10건마다 1레벨이며 알고리즘 버전을 응답에 포함한다.
- 기본 성향은 완료한 분류가 3건 이상일 때 가장 많은 분류로 정한다. 동률 우선순위는 기존 앱 규칙을 유지한다.
- 사용자 레벨은 계정의 누적 유효 완료를 기준으로 한다. 탈퇴한 집의 상세 데이터는 볼 수 없지만 본인의 누적 완료 수는 유지하는 방향을 기본 정책으로 한다.

## 4. 집과 완료 규칙

- 모든 집 조회·쓰기는 서버에서 활성 membership을 확인한다.
- 집 기본 정보와 프로필 변경, 초대 발급, 구성원 관리는 owner만 허용한다.
- 집안일은 티켓처럼 활성 구성원 1명을 선택 담당자로 지정하거나 `담당자 없음`으로 둘 수 있다.
- 담당자는 책임을 알아보기 위한 값이며 완료 권한을 제한하지 않는다. 다른 구성원이 완료하면 실제 완료자를 기록하고 `대신 완료`로 구분한다.
- 담당자 지정에는 사용자 ID가 아니라 해당 집의 membership ID를 사용한다. 다른 집 구성원이나 탈퇴한 구성원은 지정할 수 없다.
- 완료 대상은 `(homeId, choreId, scheduledFor)`로 식별하며 활성 완료는 하나만 존재한다.
- 완료 요청에는 클라이언트가 생성한 `requestId`를 포함한다. 같은 요청을 재전송하면 새 기록을 만들지 않고 기존 결과를 돌려준다.
- 해당 완료가 이후 취소됐다면 그 `requestId`는 계속 소비된 상태다. 재전송은 취소된 결과를 새 완료로 되살리지 않고 `409 IDEMPOTENT_COMPLETION_VOIDED`를 반환하며, 사용자가 다시 완료할 때는 새 `requestId`를 사용한다.
- 동시에 다른 구성원이 완료하면 먼저 확정된 기록을 canonical 결과로 돌려주고 `alreadyCompleted`로 표시한다.
- 수행자 ID와 이름은 클라이언트 값을 신뢰하지 않고 현재 세션과 DB 표시명으로 기록한다.
- 완료 당시 제목·분류·담당자 membership과 표시명을 스냅샷으로 보존한다.
- 취소는 행 삭제 대신 `voided` 상태와 취소자·시각을 기록한다.
- 집의 시간대를 기준으로 예정일과 오늘을 계산한다. MVP 기본값은 `Asia/Seoul`이다.

## 5. API 계약

### 사용자

- `GET /api/me`: 사용자 기본정보, 개인 설정, 서버 계산 레벨·성향, 참여 집 요약
- `PATCH /api/me`: 표시명, 현재 집, 알림 설정 중 전달한 필드만 변경
- `DELETE /api/account`: 개인 계정 연결 삭제, 공동 집 소유권 처리, 정책에 따른 공동 완료 이력 보존

### 집

- `GET /api/homes`: 참여 중인 집 요약 목록
- `POST /api/homes`: 집과 owner membership을 한 트랜잭션으로 생성
- `GET /api/homes/:homeId`: 집 기본정보, 내 소속·권한, 프로필, 구성원, 집안일, 오늘 예정, 최근 완료, 생활용품
- `PATCH /api/homes/:homeId`: owner가 집 기본정보와 프로필 변경
- `POST /api/homes/join`: 초대 코드로 중복 없이 참여
- `PATCH /api/homes/:homeId/chores/:choreId`: 선택 담당자를 지정하거나 해제

### 수행 이력

- `POST /api/homes/:homeId/chores/:choreId/complete`: 예정 건을 원자적으로 완료
- 후속: `POST /api/homes/:homeId/completions/:completionId/void`
- 후속: `GET /api/homes/:homeId/completions?cursor=&limit=`
- 후속: `GET /api/homes/:homeId/schedule?from=&to=`
- 후속: `GET /api/homes/:homeId/report?from=&to=`

집 상세에는 최근 완료만 포함한다. 달력과 리포트는 전체 이력을 내려받아 클라이언트에서 계산하지 않고, 기간을 명시한 별도 서버 API에서 계산한다.

완료 응답의 `occurrence.chore`는 원칙적으로 완료 ledger에 저장된 집안일 snapshot이다. migration 이전의 불완전한 legacy 결과처럼 snapshot을 복원할 수 없는 경우에만 `null`이며, 이때도 `completion.choreSnapshot`의 당시 제목·분류와 완료 감사 기록은 유지된다.

## 6. 오류 코드

| HTTP | 코드 | 의미 |
| --- | --- | --- |
| 400 | `INPUT_VALIDATION` | 길이, 날짜, 열거형 등 입력 오류 |
| 401 | `INVALID_TOSS_KEY` | 사용자 식별 실패 |
| 403 | `HOME_FORBIDDEN` | 집의 활성 구성원이 아니거나 권한 부족 |
| 404 | `HOME_NOT_FOUND`, `CHORE_NOT_FOUND` | 대상 없음 |
| 409 | `SYNC_CONFLICT` | 구형 전체 스냅샷 충돌 |
| 409 | `CHORE_OCCURRENCE_STALE` | 화면에 보인 예정 건이 이미 변경됨 |
| 409 | `IDEMPOTENT_COMPLETION_VOIDED` | 같은 요청 ID의 완료가 이미 취소됨. 다시 완료하려면 새 요청 ID 필요 |
| 500 | `SERVER_ERROR` | 내부 오류를 노출하지 않은 서버 실패 |

## 7. 단계적 전환

1. 새 Supabase 프로젝트에 기존 migration과 사용자·집 API migration을 순서대로 적용한다.
2. Vercel의 `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `SESSION_SECRET`을 새 프로젝트 값으로 교체한다.
3. `/api/health`, `/api/me`, `/api/homes`를 확인한다.
4. 완료·취소·구매 완료를 action API로 먼저 전환한다.
5. 앱 시작을 `/api/me`와 집 목록 조회로 전환하고, 선택한 집만 상세 조회한다.
6. 달력·리포트를 기간 API로 전환한다.
7. `PUT /api/state`와 무제한 전체 이력 스냅샷을 제거한다.

## 8. MVP 검증 기준

- 사용자 A가 집을 만들면 owner 소속이 같은 트랜잭션에서 생성된다.
- 사용자 B가 같은 초대 코드를 여러 번 제출해도 소속은 하나다.
- 집 구성원이 아닌 사용자는 ID를 알아도 집 상세와 완료 이력을 볼 수 없다.
- A와 B가 같은 예정 건을 동시에 완료해도 활성 완료 기록은 하나다.
- 담당자 없이 완료하거나 담당자가 아닌 구성원이 완료해도 실제 완료자와 당시 담당 상태가 정확히 남는다.
- 동일한 `requestId` 재전송은 같은 완료 결과를 반환한다.
- 취소된 완료의 `requestId` 재전송은 완료를 복구하지 않고 409를 반환하며, 새 요청 ID로만 다시 완료할 수 있다.
- 완료 뒤 원본 집안일이 삭제돼도 ledger snapshot으로 동일 요청의 완료 결과를 재생한다.
- 집안일 이름·분류 변경 또는 삭제 후에도 과거 이력의 제목·분류가 유지된다.
- 취소된 완료는 레벨·성향·리포트에서 제외된다.
- 집 하나에 많은 이력이 쌓여도 첫 화면 응답은 최근 이력만 반환한다.
- 서버가 연결되지 않았을 때 로컬 변경을 공동 집의 확정 데이터처럼 표시하지 않는다.

## 9. 정책 영향

이번 변경은 외부 결제·광고·생성형 AI·추가 개인정보 수집을 도입하지 않는다. Supabase Secret Key는 서버 환경변수에만 두며 브라우저 번들에 포함하지 않는다. 사용자 식별, 집 소속 검증, 실제 수행자 감사 기록, 탈퇴 후 접근 차단과 공동 이력 처리 방식은 앱인토스 출시 전에 실제 DB와 토스 샌드박스에서 통합 검증해야 한다. 현재 계정 삭제 후에도 공동 집의 중복 방지와 감사 가능성을 위해 당시 membership ID와 표시명 스냅샷을 공동 기록으로 보존하므로, 보존 목적·기간·삭제 요청 범위를 개인정보처리방침에 명시해야 한다.
