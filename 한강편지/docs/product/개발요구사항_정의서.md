# 한강에서 온 편지 — 개발요구사항 정의서

문서 버전: v0.1
작성 기준일: 2026-09-02
대상: 앱인토스 비게임 MVP

## 1. 목적과 범위

본 문서는 PRD의 제품 요구사항을 구현 가능한 시스템 요구사항으로 변환한다. 클라이언트, 서버, 데이터, 위치 판정, 무작위 도착, 콘텐츠 검수, 운영 도구, 보안, 테스트와 출시 기준을 포함한다.

## 2. 기술 전제

### 2.1 앱인토스 제약

- 최신 안정 버전의 앱인토스 SDK 2.x를 사용한다.
- 미니앱은 클라이언트 사이드 렌더링 또는 정적 생성 방식으로 구성하고 SSR을 사용하지 않는다.
- iframe과 외부 코드를 실행하는 `eval` 계열 기능을 사용하지 않는다.
- 번들은 압축 해제 기준 100MB 미만을 유지한다.
- 비게임 공통 내비게이션, 라이트 모드, TDS 기반 상호작용과 권한 거부 폴백을 적용한다.
- 위치와 카메라는 앱인토스 SDK 권한 설정에 명시하고 실제 토스 앱에서 확인한다.
- 서버에서 앱인토스 API를 호출할 경우 mTLS 인증서를 서버에만 보관한다.

### 2.2 권장 클라이언트 방식

MVP 권장안은 React·TypeScript 기반 WebView 미니앱과 앱인토스 Web Framework SDK 2.x다.

선정 이유는 다음과 같다.

- 일러스트형 한강 지도와 애니메이션을 SVG·Canvas로 구현하기 쉽다.
- 표준 Web API 기반 실시간 카메라 미리보기 가능성을 검증할 수 있다.
- 실시간 미리보기가 불가능해도 공식 `openCamera` 촬영 API로 폴백할 수 있다.
- MVP 기능은 네이티브 백그라운드 처리나 고성능 3D 엔진을 요구하지 않는다.

단, `MediaDevices.getUserMedia`의 iOS·Android 토스 앱 내 동작과 심사 가능 여부는 개발 첫 주 실기기 스파이크로 확정한다. 실패하면 공식 `openCamera` 기반 촬영 이미지 오버레이를 P0 구현으로 사용한다.

### 2.3 참조 기술 스택

| 계층 | 권장 구성 | 비고 |
|---|---|---|
| 미니앱 | React, TypeScript, App-in-Toss Web Framework SDK 2.x | CSR/SSG, 라이트 모드 |
| 상태·통신 | 경량 상태관리 + Fetch 계층 | 서버 상태와 UI 상태 분리 |
| 지도 표현 | 자체 SVG/Canvas 한강 일러스트 | 공원 중심점·개수만 표시 |
| API 서버 | Node.js LTS, TypeScript, Fastify 또는 NestJS | REST API, 스키마 검증 |
| 주 데이터베이스 | PostgreSQL + PostGIS | 안전 영역·제외 영역·점 판정 |
| 캐시·잠금 | Redis | 공원 재고, 발견 증표, 제한 카운터 |
| 비동기 작업 | Redis 기반 큐 또는 관리형 큐 | 검수, 도착, 재표류, 만료 |
| 콘텐츠 검수 | 공급사 독립 어댑터 | 규칙 검사 + 분류기 + 사람 검수 |
| 운영 도구 | 사내 전용 웹 콘솔 | 역할 기반 접근제어, 감사 로그 |
| 관측 | 구조화 로그, 오류 추적, 메트릭·알림 | 본문·원본 좌표 로그 금지 |

특정 클라우드 사업자는 고정하지 않는다. 데이터베이스의 PostGIS 지원, 비밀 관리, 한국 리전·개인정보 위탁 조건, 백업·복구 기능을 기준으로 선정한다.

## 3. 시스템 구성

### 3.1 논리 구조

1. 미니앱이 앱인토스 SDK에서 익명 사용자 식별키를 받는다.
2. 세션 API가 식별키를 검증하고 서비스 전용 사용자 세션을 발급한다.
3. 편지 API가 작성, 상태, 내역, 신고를 처리한다.
4. 표류 스케줄러가 도착·재표류·만료 작업을 실행한다.
5. 위치 판정 API가 사용자의 현재 좌표를 일시적으로 받아 숨은 목표 좌표와 서버에서 비교한다.
6. 반경 조건을 충족하면 Redis에 짧은 유효시간의 발견 증표를 발급한다.
7. 획득 API가 증표와 상태를 검증하고 데이터베이스 트랜잭션으로 최초 한 건만 확정한다.
8. 운영 콘솔이 안전 영역, 제외 영역, 편지, 신고와 제재를 관리한다.

### 3.2 신뢰 경계

- 미니앱의 시간, 위치, 사용자 식별 주장, 편지 상태는 신뢰하지 않는다.
- 도착 시각, 무작위 좌표, 상태 전이, 획득 소유권은 서버만 결정한다.
- 편지 실제 좌표는 미니앱에 전송하지 않는다.
- 클라이언트는 서버가 서명한 발견 증표 없이는 획득을 요청할 수 없다.
- 운영자 권한은 일반 사용자 인증과 완전히 분리한다.

| INT-AIT-004 | 위치는 `getCurrentLocation` 또는 활성 탐색 화면의 제한된 `startUpdateLocation`으로만 사용한다. |
| INT-AIT-005 | 탐색 화면 종료·백그라운드 전환·컴포넌트 해제 시 위치 구독을 즉시 중단한다. |
| INT-AIT-006 | 카메라 P0 폴백은 공식 `openCamera`를 사용하고 촬영 이미지를 서버에 업로드하지 않는다. |
| INT-AIT-007 | 앱인토스 서버 API 호출용 mTLS 인증서·개인키는 비밀 저장소에 보관하고 번들·로그·저장소에 포함하지 않는다. |
| INT-AIT-008 | 샌드박스 mock 식별키뿐 아니라 출시 QR을 통한 실제 토스 앱 테스트를 수행한다. |

## 6. API 요구사항

모든 API는 `/v1` 버전을 사용하고 JSON 스키마 검증, 인증, 요청 ID, 표준 오류 형식을 적용한다. 본문과 원본 위치가 포함된 요청은 접근 로그의 body 수집을 끈다.

### 6.1 사용자와 세션

| Method | Path | 기능 |
|---|---|---|
| POST | `/v1/session` | 앱인토스 익명 식별키 검증, 사용자 생성·조회, 단기 세션 발급 |
| DELETE | `/v1/me` | 사용자 데이터 삭제·탈퇴 요청 |
| GET | `/v1/me/limits` | 발송·획득 남은 횟수와 제한 해제 시각 |

### 6.2 편지

| Method | Path | 기능 |
|---|---|---|
| POST | `/v1/letters` | 편지 제출과 검수 작업 생성 |
| GET | `/v1/me/letters` | 내가 띄운 편지 목록·상태 |
| GET | `/v1/me/found-letters` | 내가 획득한 편지 목록 |
| GET | `/v1/found-letters/{id}` | 획득자에게만 편지 본문 반환 |
| DELETE | `/v1/me/letters/{id}` | 발신 편지 삭제 요청 |

`POST /v1/letters`는 클라이언트 멱등키를 받아 중복 탭·재시도로 동일 편지가 여러 번 생성되지 않게 한다.

### 6.3 공원과 탐색

| Method | Path | 기능 |
|---|---|---|
| GET | `/v1/parks` | 활성 공원 중심점, 운영 상태, 미획득 편지 개수 |
| GET | `/v1/parks/{id}` | 공원 정보·안전 안내·운영 시간 |
| POST | `/v1/hunts` | 해당 공원의 탐색 세션 시작 |
| POST | `/v1/hunts/{huntId}/scan` | 현재 위치를 일시 검증하고 발견 여부 반환 |
| POST | `/v1/claims` | 발견 증표로 독점 획득 확정 |

`scan` 응답은 `detected`, `claimToken`, `visualSeed`, `expiresAt`만 반환하며 편지 목표 좌표와 거리를 반환하지 않는다. `detected=false`일 때도 근접 거리나 방향을 추론할 수 있는 값을 반환하지 않는다.

### 6.4 신고

| Method | Path | 기능 |
|---|---|---|
| POST | `/v1/found-letters/{id}/reports` | 편지 신고와 신고자 화면 숨김 |
| GET | `/v1/me/reports/{id}` | 신고 처리 상태 확인 |

### 6.5 표준 오류

| 코드 | 의미 | 사용자 처리 |
|---|---|---|
| `LOCATION_PERMISSION_REQUIRED` | 위치 권한 없음 | 권한 목적·설정 안내 |
| `LOCATION_ACCURACY_LOW` | 정확도 기준 미달 | 멈춘 뒤 재시도 |
| `OUTSIDE_PARK` | 공원 경계 밖 | 공원 도착 안내 |
| `NO_LETTER_DETECTED` | 반경 안 편지 없음 | 좌표·방향 없이 계속 탐색 |
| `CLAIM_TOKEN_EXPIRED` | 발견 증표 만료 | 현장에서 다시 탐색 |
| `LETTER_ALREADY_CLAIMED` | 다른 사용자 선점 | 재고 갱신 후 복귀 |
| `SELF_CLAIM_NOT_ALLOWED` | 본인 편지 | 다른 편지 탐색 안내 |
| `DAILY_LIMIT_EXCEEDED` | 일일 제한 초과 | 해제 시각 표시 |
| `PARK_PAUSED` | 공원 운영 중지 | 다른 공원 안내 |
| `CONTENT_REJECTED` | 콘텐츠 검수 거절 | 안전한 수정 안내 |

## 7. 무작위 도착 알고리즘

### 7.1 공원 선택

1. 현재 시각에 `ACTIVE`이고 운영 시간 안인 공원을 조회한다.
2. 재고 상한 미만이며 유효한 안전 탐색 영역이 있는 공원만 남긴다.
3. 재표류라면 이전에 거친 공원을 제외한다.
4. 후보가 있으면 암호학적으로 안전한 난수로 균등 무작위 선택한다.
5. 후보가 없으면 도착을 지연하고 지수 백오프로 재시도하며 운영 경고를 보낸다.

인기, 사용자별 위치, 결제 여부, 편지 내용은 공원 선택 가중치로 사용하지 않는다.

### 7.2 좌표 생성

1. 선택한 공원의 활성 안전 탐색 영역 전체 면적을 계산한다.
2. 면적 비율에 따라 영역을 선택한다.
3. 영역의 경계 상자 안에서 후보점을 생성하고 영역 내부인지 검사한다.
4. 활성 제외 영역과 `buffer_m` 이격 기준을 통과하는지 검사한다.
5. 공원 경계, 수변·차도 최소 이격, 기존 편지 간 최소 거리, GPS 취약 구역 규칙을 검사한다.
6. 통과한 최초 후보를 확정하고 실패 시 최대 횟수까지 반복한다.
7. 반복 실패 시 해당 공원을 제외하고 공원 선택부터 다시 수행한다.

### 7.3 품질 검증

- 속성 기반 테스트로 생성 좌표가 항상 허용 영역 안이고 제외 영역 밖인지 확인한다.
- 공원·영역별 대량 표본의 분포를 검정해 편향을 탐지한다.
- 알고리즘 버전과 생성 시도 수를 기록해 운영 문제를 추적한다.

## 8. 위치 탐색과 발견 증표

### 8.1 탐색 세션

- 공원당 한 사용자에게 활성 탐색 세션 하나만 허용한다.
- 세션은 기본 30분 후 만료하며 사용자가 화면을 종료하면 즉시 종료한다.
- `scan` 호출은 기본 5초 간격으로 제한하고 백그라운드에서는 중단한다.
- 클라이언트는 가능한 높은 정확도를 요청하되 배터리와 OS 정책을 존중한다.

### 8.2 서버 판정

서버는 요청의 위도, 경도, 정확도, 측정 시각을 일시 메모리에서 사용한다.

- 측정 시각이 서버 시각 기준 60초 이상 오래되면 거절한다.
- 정확도가 운영 기준보다 나쁘면 거절한다.
- 공원 경계 또는 완충 영역 안인지 확인한다.
- 사용자의 편지를 제외한 활성 도착 편지 중 획득 반경 안의 후보를 조회한다.
- 여러 후보가 있으면 가장 먼저 도착했거나 난수로 한 편을 선택하되 목표 좌표는 반환하지 않는다.
- 성공 시 사용자·편지·landing·hunt에 묶인 2분 TTL 발견 증표를 Redis에 저장한다.

원본 사용자 좌표는 데이터베이스, 분석, 일반 로그에 저장하지 않는다. 보안 탐지에 필요한 경우에도 공원 단위 또는 넓은 격자 수준으로 즉시 축약한다.

## 9. 독점 획득 처리

### 9.1 트랜잭션 요구사항

1. 발견 증표의 서명·TTL·사용자·편지·landing을 검증한다.
2. 편지와 활성 landing 행을 잠근다.
3. 편지 상태가 `LANDED`이고 획득자가 비어 있는지 확인한다.
4. 발신자와 획득자가 다른지 확인한다.
5. `claims.letter_id UNIQUE` 제약으로 중복 획득을 방지한다.
6. claim 생성, letter의 `CLAIMED` 전이, landing의 `CLAIMED` 전이와 공원 재고 감소를 한 트랜잭션에서 커밋한다.
7. 커밋 후에만 편지 본문을 복호화해 성공 사용자에게 반환한다.

### 9.2 동시성 기준

- 동일 편지에 100개 동시 요청을 보내도 성공은 한 건이어야 한다.
- 네트워크 재시도는 멱등키로 동일 결과를 반환한다.
- 재고 캐시는 커밋 후 무효화하고 10초 안에 사용자 화면에 반영한다.

## 10. 콘텐츠 검수

### 10.1 파이프라인

1. 형식 검사: 길이, 제어문자, 반복문자, URL, 연락처, 계정 ID
2. 규칙 검사: 금칙어, 광고 패턴, 만남·거래 유도
3. 자동 분류: 혐오·괴롭힘·성적 내용·폭력·불법·자해·개인정보 위험
4. 의사결정: PASS, HOLD, REJECT
5. HOLD 사람 검수: 운영 시간 안 목표 SLA 적용
6. 사후 신고: 즉시 숨김, 위험도에 따라 전체 숨김·제재

### 10.2 구현 기준

- 검수 공급사 호출은 어댑터 인터페이스로 격리한다.
- 모델명·정책 버전·결정·지연시간을 기록한다.
- 외부 검수사로 본문을 전송할 경우 개인정보 처리 위탁·국외 이전 여부를 검토한다.
- 검수 실패나 시간 초과 시 기본값은 공개 보류이며 자동 통과시키지 않는다.
- 편지 본문을 HTML로 해석하지 않고 평문으로 이스케이프해 표시한다.

### 11.1 위치 조작 대응

앱인토스 환경에서 완전한 기기 무결성 검증을 전제하지 않는다. MVP에는 금전 보상이 없으므로 피해 기반으로 대응한다.

- 오래된 위치, 낮은 정확도, 비정상적으로 빠른 공원 간 이동을 거절 또는 위험 신호로 기록한다.
- 공원 단위 축약 이벤트로 반복 획득·자동화 패턴을 탐지한다.
- scan·claim 속도 제한과 발견 증표를 적용한다.
- 의심 사용자의 획득 제한은 가능하되 원본 위치를 장기 보관하지 않는다.

## 15. 배포와 환경

- `local`, `development`, `staging`, `production` 환경을 분리한다.
- staging은 가상 위치와 테스트 공원 데이터를 지원하되 production 설정과 분리한다.
- production 배포 전 타입 검사, 린트, 단위·통합·보안 테스트와 번들 크기 검사를 자동화한다.
- 데이터베이스 마이그레이션은 전진 호환 방식으로 실행하고 롤백 계획을 기록한다.
- 앱인토스 샌드박스 후 출시 QR로 실제 토스 앱을 확인한 뒤 검수를 요청한다.
- 클라이언트와 API의 버전 호환 범위를 명시하고 강제 업데이트 없이 점진 배포 가능하게 한다.

## 16. 개발 순서와 예상 일정

권장 팀은 제품 책임자 1명, 디자이너 1명, 클라이언트 1~2명, 백엔드 1~2명, QA·운영 각 0.5명 이상이다. 법률·콘텐츠 안전 검토는 병행한다.

| 단계 | 기간 초안 | 결과물 |
|---|---|---|
| 0. 기술 스파이크 | 1주 | 실시간 카메라/촬영 폴백, 위치, 익명키, PostGIS 검증 |
| 1. 기반 구축 | 1주 | 세션, 데이터 모델, 공원·영역 관리, CI/CD |
| 2. 보내기 루프 | 1~2주 | 작성, 검수, 표류, 도착, 내 편지 |
| 3. 찾기 루프 | 2주 | 공원 재고, 탐색 세션, scan, AR풍 연출, 독점 claim |
| 4. 안전·운영 | 1주 | 신고, 제재, 공원 중지, 감사 로그, 모니터링 |
| 5. 현장 베타 | 1~2주 | 5개 공원 데이터, 실기기·현장 QA, 반경 튜닝 |
| 6. 검수·출시 | 1주+ | 정책 보완, 앱인토스 검수, 공개 MVP |

전체는 병렬 진행 시 약 8~10주를 기본 추정으로 삼되, 위치기반서비스 법률·신고와 앱인토스 사전 협의 일정은 별도로 관리한다.
